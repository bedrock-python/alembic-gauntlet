# Project profile

## About

- What this repository is: `alembic-gauntlet`, a pytest toolkit that runs a project's Alembic migrations against a real PostgreSQL database, published on PyPI.
- Who uses it: projects with an Alembic migration history on PostgreSQL. Their test suites inherit `MigrationTestBase` and get seven migration tests.
- Language, version and main frameworks: Python 3.10 and newer. Alembic, SQLAlchemy 2 (async engine) and pytest; the package registers as a pytest plugin (`pytest11` entry point `alembic_gauntlet.fixtures`). PostgreSQL only. Optional extras: `asyncio` (pytest-asyncio, which consumers need in practice) and `testcontainers` (a PostgreSQL container fixture in `alembic_gauntlet/contrib/testcontainers.py`).
- Where the documentation lives: https://bedrock-python.github.io/alembic-gauntlet/, built with Zensical from `docs/` (`zensical.toml`). `docs/agents.md` is the one-page reference for coding assistants.

## Commands

| Task | Command |
|---|---|
| Install dependencies | `uv sync --group dev` (`make install`). The `dev` group includes the `test` group (pytest-asyncio, asyncpg, testcontainers), so no extras are needed. |
| Format | `make fmt`: `uv run ruff format .`, then `uv run ruff check --fix .` |
| Lint and type-check | `make check`: `uv run ruff check .`, `uv run ruff format --check .`, `uv run mypy alembic_gauntlet` |
| Test | `make test-unit` (`uv run pytest -m unit`), no Docker needed. `make test-integration` (`uv run pytest -m integration`) needs Docker. `make test` runs both with coverage and fails under 63%. CI runs `uv run pytest -m unit` on Python 3.10, 3.11, 3.12 and 3.13, and `uv run pytest -m integration --cov=alembic_gauntlet --cov-report=xml --cov-fail-under=90` once. |
| Run locally | A library: nothing to run. The docs: `make docs-serve`. |
| Stop the local run | Ctrl+C in the terminal of `make docs-serve`. |

## Conventions

- Default branch: `master`. A ruleset requires a pull request and the `All checks passed` CI job for every change to it. The pre-commit hook `no-commit-to-branch` refuses local commits to it.
- Issue tracker: GitHub Issues of this repository; refer to an issue as `#123`.
- Branch names: `<type>/<short-description>`, such as `feat/my-feature` (CONTRIBUTING.md).
- Commit messages: Conventional Commits, enforced by the `conventional-pre-commit` hook (`uv run pre-commit install --hook-type pre-commit --hook-type commit-msg` installs every hook; CONTRIBUTING.md installs only the commit-message one, so ruff does not run at commit time). Pull requests are squash-merged, and release-please reads the squash title, so a pull request's title is a Conventional Commit too.
- Language of pull request titles and descriptions: English.
- Where specs and design notes go: in the pull request description; the repository has no place for them.

## Boundaries

- `CHANGELOG.md` is generated by release-please: never edit it by hand, and never add an `## [Unreleased]` section, whatever the pull request template's checklist says. `docs/changelog.md` is a git-ignored copy made by the docs build.
- The version lives in `alembic_gauntlet/__version__.py`, on the line marked `# x-release-please-version`, and in `.release-please-manifest.json`; release-please bumps both. Never change them by hand.
- `docs/agents.md` is part of the public API: it changes in the same pull request as the API (CONTRIBUTING.md, "The agents page").
- Files from the engineering-assets hub (`AGENTS.md` explains how it works) include the copy-page files (`docs/assets/javascripts/copy-page.js`, `docs/assets/stylesheets/copy-page.css`, `overrides/main.html`, `scripts/emit_markdown.py`), `.github/workflows/docs.yml`, `.github/workflows/release-please.yml`, `.github/dependabot.yml`, `.editorconfig` and `CODE_OF_CONDUCT.md`. Change them in the hub; a change here makes the file this repository's own.
- Never publish to PyPI or create a release by hand: release-please creates the release, and `publish.yml` publishes it.

## Notes

- Releases: release-please opens its pull request with the workflow's own token, so CI does not start on it, and the required `All checks passed` check blocks the merge. Close and reopen the release pull request to run CI, then merge it. `publish.yml` publishes to PyPI when the Release Please run on `master` succeeds and the commit carries an `alembic-gauntlet-v*` tag. Before 1.0, a breaking change bumps the minor version (`bump-minor-pre-major`).
- Tests: `tests/conftest.py` marks every test `unit` or `integration` by its directory (`--strict-markers`). Integration tests get `migration_db_url` from `alembic_gauntlet.contrib.testcontainers` (a `postgres:17-alpine` container) and migrate the small Alembic projects in `tests/integration/sample_app*/`, which are test data. `tests/conftest.py` also sets the coverage threshold to 0 when only integration tests run, so CI's `--cov-fail-under=90` enforces nothing; only `make test` (63%) enforces a threshold.
- There is no `.python-version`: uv uses the newest Python it finds, which can be newer than CI's 3.10–3.13 matrix.
- Code style (CONTRIBUTING.md): type hints on every function, tests included; Google-style docstrings on the public API only; lines up to 120 characters; double quotes; comments only for a non-obvious why.
